# Add a Dedicated Browser Window

## Summary
Add a desktop-only browser action beside the existing context/status, terminal, and review controls. Clicking it opens or focuses one reusable Forge browser window containing an address bar and embedded web content; the web build will not render the action.

## Context / Findings
- `packages/app/src/components/session/session-header.tsx` owns `SessionHeaderQuickActions`, the target icon row.
- `packages/app/src/context/platform.tsx` is the renderer-to-platform capability boundary and currently exposes external URL opening but no browser-window action.
- Electron capabilities cross `packages/desktop/src/preload/types.ts`, `preload/index.ts`, and `main/ipc.ts`.
- `packages/desktop/src/main/windows.ts` manages Forge windows, but its navigation policy intentionally rejects arbitrary web navigation; browser navigation needs a separate policy.
- No `BrowserView`, `WebContentsView`, or embedded browser abstraction currently exists.
- `packages/opencode/src/mcp/browser.ts` only opens the OS browser for OAuth; `webfetch` and `websearch` are non-interactive model tools.
- The browser should be Electron desktop-only, start blank, reuse/focus one window, and provide a Forge-owned browser shell with address bar/navigation controls.
- The repository has localization parity requirements and existing desktop/app test patterns.

## Approach
Create a dedicated Electron `BrowserWindow` whose renderer is a small Forge-owned browser shell. Keep browser content in a separate `WebContentsView` owned by the main process, while the shell provides the address bar and navigation controls. Expose only a narrow `openBrowser` capability to the app; keep browser lifecycle, URL validation, popup handling, permissions, and downloads in the desktop main process. Do not modify server, SDK, MCP, or agent tool layers for this initial user-facing feature.

## Files affected
- `packages/app/src/components/session/session-header.tsx` — add the desktop-only browser quick-action beside terminal/review.
- `packages/app/src/context/platform.tsx` — add optional `openBrowser()` capability to the platform contract.
- `packages/app/src/i18n/en.ts` and locale dictionaries — add browser button/command labels with key parity.
- `packages/ui/src/v2/components/icon.tsx` — add the browser/globe icon (and active variant if needed).
- `packages/desktop/src/main/browser-window.ts` — create the singleton browser window, shell contents, embedded page view, focus/reuse behavior, and cleanup.
- `packages/desktop/src/main/browser-navigation.ts` — pure URL/protocol and popup policy helpers, if separated for testability.
- `packages/desktop/src/main/ipc.ts` — validate renderer senders and register the browser-open IPC handler.
- `packages/desktop/src/preload/types.ts` — type the browser IPC capability.
- `packages/desktop/src/preload/index.ts` — expose `openBrowser()` through `contextBridge`.
- `packages/desktop/src/renderer/index.tsx` — provide the desktop platform implementation and browser-shell renderer route/entry point.
- `packages/desktop/src/main/browser-window.test.ts` — test singleton lifecycle and navigation policy.
- `packages/desktop/src/main/browser-navigation.test.ts` — test allowed and rejected URL schemes.
- `packages/app/src/components/session/session-header.test.tsx` or the nearest existing component test location — verify desktop visibility, web omission, and click behavior.
- `packages/app/src/i18n/*.ts` — add the localized browser labels required by dictionary parity.

## Step-by-step implementation
1. Define the browser-shell contract: blank initial page, address input, back, forward, reload, loading/error state, external-link behavior, and one reusable native window.
2. Add a dedicated browser-window manager in the Electron main process. Create/focus one window, clear its reference on close, and keep it separate from persisted Forge main-window restoration.
3. Create the browser shell renderer with a secure Forge preload. Attach a `WebContentsView` for arbitrary web content below the shell controls; resize it with the window and keep browser content isolated from Forge APIs.
4. Add typed IPC for opening/focusing the browser and for shell-to-main navigation commands/state updates. Validate IPC senders and main-frame ownership.
5. Implement strict browser navigation policy: allow `about:blank`, `http:`, and `https:`; reject `file:`, `javascript:`, `data:`, custom schemes, malformed URLs, and uncontrolled child windows. Route unsupported external actions through the system browser where appropriate.
6. Add conservative permission and download handling. Default-deny camera, microphone, geolocation, notifications, and similar permissions; do not silently write downloads. Defer persistent profiles, password storage, and arbitrary download destinations unless explicitly requested.
7. Add the platform capability and desktop implementation, then add the browser icon to `SessionHeaderQuickActions`. Hide it on web rather than showing a nonfunctional disabled control. Use existing `TooltipV2`, `IconButtonV2`, pressed/hover styling, and localized accessible labels.
8. Add the new icon and localization keys across all app dictionaries. Keep the native browser window title localized through the desktop translation bundle if a title is shown.
9. Add unit tests for singleton reuse/close behavior, URL policy, popup policy, IPC validation, and shell navigation state. Add an app test that desktop renders/calls the action while web does not.
10. Run package-local typechecks/tests from `packages/app` and `packages/desktop`, then perform a packaged desktop smoke test on the supported platforms. Record the existing app timeline benchmark baseline before changing the session header and compare it afterward.

## Risks / edge cases
- A `BrowserWindow` alone cannot provide browser controls; the Forge shell and `WebContentsView` must remain separate from arbitrary page content.
- Reusing the main Forge navigation policy or preload would expose unsafe assumptions and potentially privileged APIs to web pages.
- Popup windows, OAuth redirects, custom protocols, downloads, certificates, and permission prompts require explicit policy.
- A persisted browser session can retain sensitive cookies; the initial implementation should use an isolated session partition and make persistence an explicit later decision.
- Browser-only desktop functionality must not break the web app or server-side rendering paths.
- Existing OAuth flows intentionally use the system browser; this feature should not silently migrate MCP OAuth into the embedded browser.
- The repository currently has uncommitted Plan Mode changes; implementation should avoid overwriting them.

## Testing strategy
- Unit-test browser URL/protocol validation and popup decisions as pure functions.
- Unit-test singleton browser-window creation, focus/reuse, close cleanup, and failure handling with Electron window factories.
- Test IPC sender validation and renderer/preload capability wiring.
- Test the quick-action component for desktop-only rendering, localization, icon presence, and click invocation.
- Manually verify blank startup, address navigation, back/forward/reload, reload after close/reopen, blocked unsafe schemes, popup behavior, and external-link handling.
- Run `bun typecheck` and relevant tests from `packages/app` and `packages/desktop`; do not run tests from repository root.

## Open questions
- Whether browser cookies/session state should persist across application restarts; this plan defaults to an isolated non-persistent session until decided.
- Whether downloads should be supported in the first release; this plan defaults to safe rejection or explicit native-save handling rather than silent downloads.
