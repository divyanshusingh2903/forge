# Fix washed-out Keybind numbers on plan-mode Yes/No buttons

## Summary
Fix the `1` / `2` `Keybind` pills in the plan-mode question dock looking flushed/washed-out on the primary `Yes` button in dark mode by making the on-primary keybind treatment theme-aware instead of hardcoded white-on-dark.

## Context / Findings
- Prompt string lives in `packages/opencode/src/tool/plan.ts:118-144` (`PlanEnterTool`), rendered via `question.ask`.
- Exact dialog in screenshot is `packages/app/src/pages/session/composer/session-plan-question-dock.tsx:34-133` (`SessionPlanQuestionDock`), routed in `session-composer-region.tsx:40-55` for `plan_enter` / `present_plan`.
- Ordering/variants: `RANK = { No:0, Yes:3 }`, `No` -> `ghost` + `Keybind 1`, `Yes` -> `primary` + `Keybind 2` (`session-plan-question-dock.tsx:18-56,118-125`). Same convention as `session-permission-dock.tsx:22-84`.
- Badge component is `Keybind` (`packages/ui/src/components/keybind.tsx:8-20`, `keybind.css:1-28`), not `Badge`/`Kbd`/`keybind-v2`.
- Root cause: `keybind.css:24-28` hardcodes `background: rgba(255,255,255,0.16); color: rgba(255,255,255,0.7)` assuming primary is always dark. True in light theme (`theme.css:195 --button-primary-base: #171717`, `249 --icon-invert-base: #ffffff`), false in dark theme (`theme.css:466 --button-primary-base: #ededed` light, `520 --icon-invert-base: #161616` dark text). Result: white-on-light `2` on the light `Yes` button = flushed.
- Same bug affects `SessionPermissionDock` primary `Allow once / 3` badge.

## Approach
Keep the subtle-pill intent but derive the on-primary treatment from the button's own contract tokens (`--icon-invert-base`) via `color-mix`, so polarity auto-tracks light/dark without `data-theme` branches or hardcoded hex. Single-rule CSS change; no dock component changes.

## Files affected
- `packages/ui/src/components/keybind.css` — replace hardcoded white rgba in `[data-component="button"][data-variant="primary"] [data-component="keybind"]` with `color-mix(in srgb, var(--icon-invert-base) 16%, transparent)` background + `var(--icon-invert-base)` text (tune opacity 60-75% for 12px legibility).
- No changes to `session-plan-question-dock.tsx`, `session-permission-dock.tsx` (consumers already correct). Only add explicit `--keybind-on-primary-*` tokens in `packages/ui/src/styles/theme.css` if designers want opacity decoupled.

## Step-by-step implementation
1. In `keybind.css`, replace the primary override background/color with `color-mix` veil derived from `var(--icon-invert-base)`; keep `box-shadow: none`.
2. Verify contrast in both themes: light (`#171717` bg + white veil/text) and dark (`#ededed` bg + dark veil/text).
3. Check hover/focus/active/disabled states inherit correctly (primary hover uses `--icon-strong-hover/active/focus`; disabled dims via `button.css:32-38` — badge must not stay full-contrast).
4. Regression-check `SessionPermissionDock` (`1/2/3`) and `present_plan` dock (ghost `Open plan` button has no badge, numbered options do).
5. Run `bun typecheck` from `packages/ui` (or affected package dir), never `tsc` directly.

## Risks / edge cases
- Translucent `color-mix` text at 12px may still be low contrast — fallback is solid inverted pill (`background: var(--icon-invert-base); color: var(--button-primary-base)`) at cost of heavier visual weight.
- Ghost/secondary badges use default `var(--surface-base)` + `var(--text-weak)` path — untouched, but confirm `text-weak` on `button-secondary-base` still passes after change.
- Forced-colors / high-contrast may flatten translucency — solid `color` alone must still contrast.
- `color-mix` support: safe in Electron/Chromium, verify no legacy target breaks.
