# Create a chapters feature issue hierarchy

## Context

Forge has no persisted chapter, bookmark, or milestone entity. The V2 projected timeline is ordered by durable message sequence (`packages/core/src/session/sql.ts`) and the app already supports virtualized deep links to user messages through `#message-<id>` in `packages/app/src/pages/session/use-session-hash-scroll.ts`.

Upstream OpenCode V2 contains TUI previous/next message shortcuts (`upstream/v2` commit `5ee4c1082a`) and experimental timeline history/grouping branches, but no user-created or persisted chapter implementation. The chapter feature therefore does not duplicate an active upstream feature, but must reuse Forge's message anchors and timeline loading rather than introduce a parallel navigation path.

GitHub search found no existing Forge issue covering chat chapters, bookmarks, or timeline milestones. Repository issue types include `Feature` and `Task`.

## Design decisions

Create one `Feature` parent issue with four child `Task` issues.

Represent a chapter as a durable, session-scoped annotation anchored to a user-message ID and its sequence. Store it outside model-visible `session_message` metadata so it cannot change LLM history or provider requests.

Support manual named chapters and automatic chapter suggestions derived only from explicit workflow transitions, initially plan-cycle, agent, and task-workflow changes. Do not add LLM topic detection; it adds cost and nondeterministic section boundaries. Suggested chapters must be editable or removable by the user.

Use the existing hash-scroll and paged-history mechanism for navigation. This preserves virtualized timeline behavior and lets a chapter jump to older, unloaded messages.

## Changes

### GitHub feature issue: Chapters for long-running sessions

Describe the user outcome: a durable, editable outline for returning to work phases in long sessions. Record upstream findings, the non-model-visible storage boundary, and acceptance criteria covering manual chapters, automatic workflow-transition suggestions, navigation, and deletion/revert behavior.

### Child task: Persist chapter annotations and expose V2 CRUD

Define the chapter schema, `session_chapter` persistence, migration, Core operations, Protocol/Server endpoints, generated-client workflow, and lifecycle behavior. Require target user-message validation, stable ordering by target sequence, ownership/session isolation, and cascade deletion of chapters whose target messages are removed by a committed revert.

### Child task: Generate editable workflow-transition chapter suggestions

Define deterministic integration points for plan-cycle, agent, and task-workflow transitions. Persist suggested chapters through the same chapter API with source metadata; title them from explicit transition metadata; prevent duplicate suggestions for the same transition; let users rename or delete them. Explicitly exclude model topic inference.

### Child task: Build the desktop/web chapter outline and navigation

Fetch/cache chapters with session data; add accessible chapter-list controls for creation, selection, rename, and removal; and route selection through `useSessionHashScroll` rather than DOM-only scrolling. Make chapter navigation load earlier paginated history and work with timeline virtualization. Present manual and suggested chapters distinctly without disrupting existing message keyboard navigation.

### Child task: Cover chapter lifecycle and long-timeline regressions

Add Core/Protocol tests for CRUD, session isolation, target validation, ordering, duplicate automatic transitions, and revert cleanup. Add app tests for hash navigation to unloaded targets plus Playwright coverage for a long virtualized session, keyboard/mouse chapter selection, renaming/removing markers, and persisted state after reload.

## Out of scope

- LLM-generated topic segmentation or titles.
- Replacing existing previous/next message shortcuts or hash deep links.
- Reusing V2 experimental timeline lineage/grouping branches as a chapter schema.
- Modifying session execution, durable input admission, or model history.

## Verification

Verify each created GitHub issue has the intended type, parent-child hierarchy, repository-backed paths, and independently testable acceptance criteria. Search issues before creation confirmed no duplicate exists.

Implementation verification, to be captured in the child tasks, includes Core and Protocol test suites, client generation after public API changes, app typechecking, and focused virtualized-timeline Playwright regressions.
