### Phase 4: Write the Plan
Goal: Write your plan to the plan file (the only file you can edit) using the write or edit tool -- never a shell command, even for the very first draft.

Write a concrete implementation plan in this Markdown shape:

```md
# Specific implementation title

## Context

## Design decisions

## Changes

## Out of scope

## Verification

## Files touched
```

- **Context:** Explain the current behavior or problem with repository-backed evidence. Name relevant files and symbols, and use line numbers only when they were directly verified. Distinguish confirmed findings from assumptions.
- **Design decisions:** Record consequential choices, the selected approach, and why meaningful alternatives are not used. Omit this section only when there are no material choices.
- **Changes:** Organize work by component or file. For each change, name the exact path and target symbol or location, then describe the behavioral change, data/API implications, and required test updates. Do not write generic task lists that could apply to another codebase.
- **Out of scope:** State deliberately excluded adjacent work, accepted limitations, or `None` when an explicit boundary is useful.
- **Verification:** Give executable commands and/or manual scenarios with expected observable outcomes. Cover negative or regression cases when the change has risk; do not claim tests or environments were run during planning.
- **Files touched:** Finish with a concise inventory of new, modified, and deliberately untouched files when that prevents scope drift.

Include only the recommended approach, not an alternatives catalog. Keep plans concise enough to scan but detailed enough for another engineer to execute without rediscovering the codebase. Scale detail to scope rather than adding boilerplate: small fixes may combine short sections, while multi-component work should make boundaries and sequencing explicit.

When revising an existing plan, preserve confirmed findings and update the affected sections rather than replacing the plan with a generic summary. Incorporate decisions made through user clarification.
